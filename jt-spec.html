判定表结构化字段规范 + 样表（JT-01）

收益管理 15 张判定表体系 · AI 引擎母本规范 v0.1

用途：这是把 15 张判定表喂给「判定表决策引擎 / XX 教练分身」的统一可机读格式。 样表取自教材第 1 张判定表「降价前先算这一步」，按下方规范重新结构化， 同时给出人读视图与机读 JSON 两种形态——JSON 即引擎可直接消费的输入。

一、统一字段规范

所有判定表按此字段落库；缺省项可空，但 id / title / domain / trigger / inputs / decision_logic / rules / version 为必填。

字段类型必填说明样例
idstring是稳定唯一标识，格式 JT-NN（两位补零）JT-01
titlestring是判定表主题（人读标题）降价前先算这一步
chapterstring是所属章/篇，用于教材定位第1章·认知与衡量
domainenum是业务域：定价 / 预测 / 库存 / 渠道 / 会议 / 综合定价
tagsstring[]否检索标签，便于引擎与社区索引["降价","打平","栅栏"]
triggertext是何时该查这张表（触发场景）想用降价冲量提升业绩时
preconditionstext否查表前需备齐的数据/前提已知降价幅度、当前出租率
inputsobject[]是引擎输入变量：{name, desc, type, unit, range, example}见样表
derivedobject[]否由输入算出的中间量：{name, formula, desc, example}打平所需出租率涨幅
decision_logictext是怎么读这张表（逐条匹配 / 矩阵查行）自顶向下逐条判定，命中即取 then
rulesobject[]是判定规则集：{when, then:{decision, action, rationale}}见样表
basistext否背后的原理 / 公式收入变动=(1+量%)(1+价%)−1
pitfallstext否反例 / 常见坑分母口径错→查错一格
data_needsstring[]否酒店需喂给引擎的数据项["降价幅度%","当前OCC"]
confidenceenum否置信 / 适用边界：高 / 中 / 条件适用高（通用）
relatedstring[]否关联判定表 ID["JT-05"]
versionstring是规范/内容版本v0.1

二、样表 JT-01 · 降价前先算这一步

原表出自教材第 1 章（books-set/01-第一篇-认知与衡量.md）。下方为按规范重构后的双视图。

人读视图 · 决策规则

触发：任何想用「降价冲量」来提升业绩的念头出现时。
决策逻辑：先算打平所需涨幅 → 判断该涨幅当下是否现实 → 现实才考虑降，且必须配栅栏只降给新增客源。

① 当 打平所需出租率涨幅 > 当前可实现的涨幅（如淡季）
决策：不降
动作：维持原价，改用非价格手段（服务/打包）。
依据：降价带来的量增补不回价损，RevPAR 与 GOPPAR 双降。
② 当 涨幅现实，但无法限定降价对象
决策：不降或慎用
动作：避免全量降价。
依据：全量降价会拉低已愿意付高价的客源价格，得不偿失。
③ 当 涨幅现实，且能用栅栏只降给新增客源
决策：降，但要设栅栏
动作：提前预订 / 不可取消 / 限定渠道或房型，分隔新老客源价格。
依据：只让新增价格敏感客享受低价，保护原有高价客。
④ 当 降价后出租率涨幅 < 打平所需涨幅
决策：不降
动作：重新评估，或仅小幅限渠道降价。
依据：未达打平点即亏。

依据公式：收入变动 = (1+出租率变动%) × (1+房价变动%) − 1；打平条件：出租率涨幅 > 降价幅度 ÷ (1−降价幅度)。
常见坑：分母用错（OCC/RevPAR 分母是「可售房晚」，ADR 是「已售房晚」）会导致整张表查错一格；只看 OCC 不看 GOPPAR 会误判成功。
需喂数据：拟降价幅度% · 当前出租率% · 历史需求弹性或可达涨幅估算 · 可售房晚口径。
